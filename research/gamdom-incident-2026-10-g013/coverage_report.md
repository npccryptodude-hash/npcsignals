# Coverage, sources and verification standard

Newly acquired: two BNB locker-deposit transactions/receipts/headers, bounded source-receiver USDT outgoing log searches (each settlement block through +2000 blocks), four selected USDT balance states; historical source locker bytecode, source/ABI and nonce storage/message/chain/key calls; historical empty code for both BNB deposit addresses and the Ethereum treasury at both payout blocks; historical NEAR WASM/account states, chain-56 public-key and locker getters; complete details for all 24 receipts belonging to G012's four NEAR executions; first-party HOT SDK/validation source blobs; protocol bridge/treasury documentation; receipt-ID and transaction-hash probes against OMFT withdrawal_status.

Frozen G012 supplies the four NEAR transaction outcomes, known Ethereum receipt/input records, order metadata/identifiers and source principal. No G005–G012 transaction investigation is restarted, and no old transaction is counted as a new transaction identity. G011 is consulted only through preserved source relationships described in G012.

All acquisition attempts appear in source_register.json. Initial legacy NEAR endpoint attempts returned HTTP 429; those exact responses remain. FastNear's documented archival endpoint supplied missing receipt details, historical code and state. Both hostnames are maintained by FastNear according to the provider's documentation; they are alternative endpoints, not claimed to be independent consensus sources. No invented credentials, authentication bypass or hidden account access was used.

Raw Solidity and TypeScript/Rust blobs are pinned by Git blob hashes and their captured repository trees. Those current repository snapshots are explanatory sources, not historical deployment equivalence proofs. For the actual source locker, independently queried historical runtime bytes equal Sourcify's chain-56 on-chain runtime. Sourcify reports runtimeMatch `match`, not `exact_match`; no local compiler reproduction is claimed. The captured deployment metadata is service evidence, not a separately verified creation transaction.

Historical HOT and DAI OMFT WASM bytes independently hash to their returned on-chain account code hashes. The code hashes agree at the two respective historical snapshots. No Rust source-to-WASM build equivalence, lifetime upgrade history or independent WASM execution is claimed. Historical intents.near code is also preserved where access succeeded but is not locally compiled/audited.

All 24 receipt details match the corresponding outcome executor and form fully connected receipt trees rooted in each transaction's reported receipt IDs. Data/refund receipts are included, not misidentified as transactions. Function-call predecessor, signer, arguments and child relationships are preserved. NEAR transaction/outcome validity is accepted through archival RPC; no receipt/Merkle/state-root proofs or independent NEP-413 signature reconstruction are performed.

Two 64-byte HOT deposit signatures are independently verified using secp256k1 ECDSA against reconstructed SHA-256 digests and historical chain-56 getter keys. No recovery ID is present; none is invented. Each new BNB type-1 signed envelope is reconstructed, transaction-hash matched and its sender key recovered. MPC node membership/quorum and global replay protection are NOT ASSESSED.

OMFT withdrawal_status is a scoped read-only endpoint discovery: probes using the two action receipt IDs returned `Withdrawals not found`; probes using the two NEAR execution transaction hashes returned completed mappings to the exact Ethereum hashes. This does not make receipt IDs interchangeable with transaction hashes. These API responses are not signed payout attestations. Service backend independence from 1Click is unknown.

Additional Ethereum internal-trace attempts were preserved: Tenderly debug_traceTransaction returned HTTP 429; PublicNode debug_traceTransaction returned JSON-RPC -32601 (unavailable); PublicNode trace_transaction returned HTTP 403. No internal payout trace is claimed. The existing complete input/receipt and new historical sender-code states establish the observed direct transfer form, not an authenticated bridge instruction.

CONFIRMED means independently reproducible on-chain/RPC or cryptographic evidence within these limits. Source deposit-message links and selected NEAR receipt relationships meet that standard. The final treasury-payment association remains SUPPORTED. Human consent, company attribution and unauthorized status remain UNRESOLVED. No numerical API `amount` field is used where precision is unsafe.
